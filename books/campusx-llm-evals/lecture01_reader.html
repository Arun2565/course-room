Why we need LLM evals ▶ 0:04

Why do we need LLM evaluations, what exactly are they, and how are they different from software testing. Up to this point in the course we have only touched the subject from a distance. Today we read the definition properly and then take it apart.

LLM evals are defined as systematic tests used to judge an LLM, and which are applied to the LLM itself as well as to the application built on top of it. Three properties matter here, and all three are important.

The three properties ▶ 0:56

First, they are systematic. Second, the tests are repeatable. Third, the tests have very clear criteria. All three are core characteristics of evals. Understand these once and the rest of the course becomes much easier.

Systematic, not casual checking ▶ 1:25

Let's take the first one. Systematic means that you are not casually testing here. It is not that five questions popped into your head, you asked them, and the answers felt right.

Instead, what you do is create datasets. You try to cover every kind of edge case in those datasets. So you test your chatbot, or your LLM-based system, the way you would actually test it. If I am building an X chatbot, what I will do is pull out a hundred real chats that happened on my system, build a dataset out of them, and run my testing on that dataset.

That is the first thing. It is systematic.

Repeatable ▶ 2:22

Second, it is repeatable. Repeatable means that if tomorrow you change your system, change the model, change the chunking strategy, and change everything else, you can still evaluate your system exactly the way you were evaluating it before.

This is a very important idea: LLM evals should be repeatable. You should be able to apply the same dataset to any version of the software and extract the results in exactly the same way.

This matters because it is what lets you compare. You have a test dataset. Version one scored some number on it. Version two scored some number on it. That tells you whether the system is getting better or not. That is what repeatable means.

Clear criteria ▶ 3:12

The thing LLM evals depend on most is what you are going to evaluate on the basis of. Suppose I am building an X chatbot. There will be many criteria I want to evaluate on.

The first answer should come out. The second should be simple to use. The third should be able to explain, and that explanation should come from our own content. The fourth should be safe. There should be nothing unsafe in it, no abuse, no abusive tone.

All of that has to hold. So what do you do? You define the criteria for the chatbot. Without you doing that, testing with criteria does not happen and you do not get a proper evaluation.

Evals are not just metrics ▶ 4:46

One thing I want to clear up here, because a lot of people are confused about it, and I was confused too the first time I heard this topic.

I came from machine learning and deep learning. Over there, evaluation meant metrics. We would say, how do you evaluate a machine learning model? We would talk about accuracy, precision, recall. So in my head, LLM evals were simply a set of numbers on the basis of which we judge performance.

That is wrong. In the very first lecture I want to tell you this: LLM evals does not mean metrics. It is the entire testing setup. The whole thing you build in order to evaluate an LLM is what we call LLM evals.

What the setup actually includes ▶ 5:41

Suppose you have a RAG chatbot. You want to evaluate the retriever inside it. The retriever is a component, and it has now become part of LLM evals. You are evaluating it on the basis of criteria: what is the retrieval accuracy?

When you run these tests, offline or in production after deployment, that is also part of the setup. Which tools you use is also part of it. Later we will use RAGAS, because it is an application, so that tool is also part of your evals.

So whenever anyone asks you what an eval is, the answer is not only metrics. LLM evals means the entire testing setup: what you are testing, on what basis, when you are running the tests, and which tool you are using to run them. All of it together is what we call evals.

This can feel confusing at this point. But be clear on this: evals is not only metrics. It is the entire testing setup.

What evals are for ▶ 7:16

What you get out of an eval is not a metric. What you get out of it is practical questions. What kind of questions? Look at these.

Which model can be used for a task application? You get the answer to this question when you do evals. Does this system ship to production? You get the answer to this when you evaluate. Did prompt version two improve over prompt version one? You can extract that answer by evaluating. Is the RAG answer, given the retrieved context, correct in completing the task? Is it safe for real users? Is the latency under control?

You get answers to these kinds of questions when you do evals. That is what LLM evals does.

I have read a lot of theory so far, and I agree that at this point it does not click. A little later in the course we will revise this whole thing through one full example, and everything will become much easier.

Model evals and application evals ▶ 8:23

Before we discuss how LLM evals work, there is one very important point I want to tell you, and it needs to be clear in your head. It will help you a lot later.

Today, evals are divided into two parts. One we call model evals. The second we call application evals.

Model evals are the evals with which we evaluate the LLM. Application evals are the evals with which we evaluate the LLM-based application.

If you go back to the previous slide, the definition there says LLM evals, and both LLM itself and the LLM-based system are written there. That is why, on the basis of this definition, there are two types of LLM evals. One we call model evals, the second we call application evals.

The job of model evals is simple: to evaluate a given LLM. The job of application evals is to evaluate the entire LLM-based application.

If this distinction becomes clear in your head right at the start, that is very good.

Model evals ▶ 9:57

Here I will give you a disclaimer. The terms model evals and application evals are not official terms. I made them up. I created them because I wanted this topic to sit properly in your head.

So do not quote me tomorrow saying model evals is a term and application evals is a term. In the industry both of them together are called evals, and on the use case people automatically understand whether model evals are being discussed or application evals.

I am giving you this in advance. Now let us understand both types of evals in a little detail, and see what exactly they do.

First, model evals. There is a definition written here: model evals evaluate the model itself. It is simple. The job is to evaluate the capabilities of the LLM. The main idea of this kind of eval is to test and benchmark the capabilities of a model.

All these evals have the same goal. When a new LLM is released, we test what its capabilities are and benchmark it.

You have probably seen this too. Whenever a new LLM is released, it is said that it came on top of a particular leaderboard, that it achieved such and such accuracy on such and such percentage. You must have noticed this at some point.

Whenever these new models come, what they always do is quote these leaderboards: on this particular leaderboard or on this particular benchmark, this LLM came out on top.

What is on those leaderboards ▶ 11:43

What is actually there? There are some evals already built. As soon as an LLM comes to the market, we test that LLM on those evals to find the level, and then we publish it on the internet so that everyone knows what the LLM is capable of.

The question now is: which types of capabilities can we test? Today's evals test roughly eight capabilities.

The eight capability categories ▶ 12:07

The first capability is reasoning. Can our model reason? Can it solve a problem by thinking through it step by step?

The second is knowledge. Does our model have basic world knowledge, general knowledge? We talk about a cutoff date. The model should have all the world's knowledge up to that cutoff date.

The third is basic maths. Can our model solve maths problems?

The fourth capability is coding. Can our LLM code?

The fifth capability is following instructions. Can our model follow instructions? If I give it ten instructions, will it follow all of them one after another?

Then comes long handling. Can our LLM pull answers out of large context?

The seventh is multimodal. Does our LLM have capabilities? Can it understand images, text, sound, or can it produce output?

And lastly, tool use. Can our model utilise tools properly?

In today's world these eight categories are the basis on which new LLMs are evaluated and documented. All of this is done on that basis.

Some famous benchmarks ▶ 13:56

Here I have written down some example benchmarks. We will discuss all the benchmarks later. If you want to check general knowledge for some model, the very famous benchmark is MMLU. It asks you questions from many different subjects: science, history, medicine. It asks your LLM those questions, records the answers, and evaluates them.

For maths, there is GSM8K, which is grade school maths, and it answers on that basis.

For coding, you have probably heard of it, it is a very famous benchmark, HumanEval. For instruction following, IFEval. For checking long context, InfiniteBench is very famous. For multimodal capabilities, there is MMMU.

Do you need to do model evals? ▶ 14:48

If we summarize the discussion so far: evals is divided into two parts, model evals and application evals. Model evals are done to test the capabilities of an LLM. These eight are the ones we have covered just now, and these tests are done with the help of benchmarks. That is our next lecture's topic. Over a full lecture I will teach you the most important benchmarks, how they are run on LLMs, how the results come out, the complete workflow.

So by the next lecture you should have a fairly good idea of model evals.

But there is one thing I want to say here. If you are going to be an AI engineer, you will not do that much work on model evals. Because think about it: evaluating a newly released LLM, benchmarking it, evaluating it, is not your job. That is the job of big frontier labs. When they bring out a new model, they test it on these benchmarks and tell you how their new LLM is.

What you should know is what model evals are, what benchmarks are, and how to read a benchmark. The benefit of that is that when you pick a new model, you already have an idea, and you know which model performs on which benchmark, and on that basis you will be able to make a better decision about which model to use in your LLM-based application.

So you will feel slightly more confident. If you know this topic, but you might never have to do model evals practically, there is a very good chance you never do them. But you should know about them. You should be able to read them.

Application evals ▶ 17:17

So that was all about model evals. Now let us talk about the second category, which is application evals. Before we discuss it, I want to tell you that this is the category you have to study properly.

This should be your topic of interest. This is the category you will do practically. Your job as an AI engineer is to build LLM-based applications, and evaluating them is also your job. Application evals is the main topic of this playlist. In this whole course we will focus on it.

There will be only one lecture on top of it, and that too, so that you understand how model evals work.

The LLM is only one thing ▶ 18:12

Application evals exist because, in an LLM, the LLM is just one thing. Beginners feel that an LLM application means LLMs, meaning the brain of it, and that everything is the LLM. That is not the case.

As you gain experience in AI, you will build bigger and bigger things, and you will realise that the brain is important, but there is a lot more you have to put around it. So that is what your LLM-based application is made of.

I have written the whole list here. Your user is one thing. The prompt you write, the system prompt, that is one thing. If you add tools, if you add APIs, that is one thing. The code you have written to run the whole system, in LangGraph, that goes from here to here. Branching from here, parallel control flow. That is one thing.

The guardrails you have at the application level are also a very important thing. If you use output, that is one thing. And let me speak about context, because context is very important. If you are building a RAG system, retrieval is separate. The embedding model you use is separate. There are vector databases. After all of that, there is a complete setup, and the complete loop.

So when you build a proper LLM application, the LLM is just one component. Beyond that, there is a lot more that you have to put in. That is why application evals is a very important topic. Evaluation alone will not do it.

The smartphone analogy ▶ 19:58

From the model we get to know how capable it is. But everything you built around it also has to work.

Take smartphones. What happens inside a smartphone? There is a chip, a Snapdragon or a MediaTek. And you will see that these chips release benchmarks: our new J2 is here, our J3 is here, the N2 score is this much. From that we find out how strong we are. Now tell me, is a good processor a guarantee that your smartphone is good, or do other things matter too?

Making a smartphone needs a lot more things. You have your camera, your operating system, your sound system, your graphics. A lot more things. And only when all of them work properly is your smartphone good.

Since there are so many things, the battery matters too, and the battery is also important. All these things work together, and only then does your smartphone run well. Just having a good processor is not enough. So all the other things you added, you have to evaluate those too.

You put in a battery, so you will test the battery. You put in graphics, so you will test that too. The same thing applies here. The frontier labs have evaluated the LLM for you. But on top of that, the complete system we built, the evaluation of that is ours, as AI engineers. We do that evaluation.

Component level and system level ▶ 22:00

I hope that is clear. What is written here in theory is: evals assess the behaviour of an LLM-powered application at the level of the entire system and at the level of a component within it.

What does the application do? It does it at the component level and it does it at the level of the whole system. If you have built a RAG, you will evaluate the whole RAG: what is its response like, what is the latency like, per token what is the cost. And you will also evaluate at the component level: is the retriever working correctly, is my embedding model working correctly, is my reranker working correctly. You get my idea.
